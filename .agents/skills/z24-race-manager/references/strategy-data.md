## 主动补取，不能停在“缺少逐圈”

主采集的三路产出不变。需要配速或交通分析时，主动执行独立的一次性补查工具（不启动第四个常驻进程），将结果写入本次目录 `analysis/`：

```sh
uv run python .agents/skills/z24-race-manager/scripts/race_laps.py --results '本次目录/all_class.csv' \
  --team '用户车队完整名称' --cars '相关对手车号,另一个车号' \
  --output '本次目录/analysis'
```

历史测试添加 `--replay-cycle`：脚本用真实当前时钟计算赛程进度，加到CSV里的真实历史开赛时间，**过滤该截止时刻以后的圈记录**，不要求用户提供日期。指定历史时刻也可用 `--at '2025-12-20T20:00:00+08:00'`。这重建了逐圈数据截至某时点的视图，不包含当时的处罚、准确官方排名或车手排班。不要混入终局排名/未来公告。

`--all-cars`用于出站交通问题，目标及全场车一并补查（最多3个并发请求）。只查目标和两个对手时，不得说已找到全场干净窗口。优先复用本轮分析文件，通常30秒内不重复同一查询。实时补查的成绩输入也必须校验身份与新鲜度。某车失败在pace.csv保留error，不应把失败车当不存在。

输出CSV同样第一行采集元数据：
- `analysis/laps.csv`：各车每圈过线时间、圈速、圈次、来源成绩ID和单车收到时间。
- `analysis/pace.csv`：近10圈中位数、MAD波动、启发式剔除圈数、前10圈中位数、配速变化、最近过线距分析时刻、假定180秒损失折合圈数。剔除超过窗口中位数1.5倍或低于0.5倍的圈；不能将异常圈直接判为进站。少于5个正常样本或过线太旧时不能可靠推位置。

默认 `--pit-cost 180` 是用户情景中的净时间损失假设，用于折合圈数；不意味着已测得真实净损失。用户有实测值时传实际值。每圈数据含时间戳，但其API传输精度不等于计时系统测量准确度。

## 没有蓝旗，不假定让车

用户明确没有蓝旗。套圈与被套圈都可能产生交通损失；不论名次、圈差，均不能默认对方让车或目标必须主动让车。比较交通风险时关注前方慢车、后方快车和车群密度，并保留超车难度未知。

## 从这些数据到进站方案

有全场较新过线记录和近期配速，可在恒速假设下估计各车一圈内相位：`phase_i(t)=((t-last_cross_i)/pace_i) mod 1`。这给的是计时线参考下的粗略赛道位置，不是GPS。异常长圈、正在进站/停驶、采样过旧的车须单独标为未知；未知车会降低“干净”结论的覆盖率。

比较现在进站、延后1圈、延后2圈等候选；每个方案必须统一参考点，并说明预计出站附近前后车、追上前车的时间与不确定性。**不能把t+180直接等同于通过维修区出口时刻**：180为净损失时，还需要正常经过相同区段的时间；维修区入口/出口相对计时线位置未知时，只能比较统一计时线上的等效相位和交通风险，明确称为候选窗口，不能保证真实出口干净。先给可算的相对优劣，再指出唯一关键的校准项，不笼统拒绝所有策略。

近期配速用中位数作基线，以波动和进站额外耗时做敏感性分析（例如用户180秒假设及+15/+30秒情景，情景不是概率预报）。如果只在单一假设下好、稍有超时即进入车群，明确称脆弱窗口。跨圈名次差不等于赛道相位差。

## 有价值的回复

先给结论，再给2—3个实际计算证据：
- 我方近期配速与变化；关键对手每圈快/慢多少，是否有持续追近趋势。
- 用户换人计划下的可用进站区间；180秒损失折合多少圈。仅最低停站规则不决定何时进站。
- 有数据时比较“现在/晚1圈/晚2圈”的交通风险，而不是只报规则最晚时刻。
- 公告变化是否改变当前选择；雷达变化是否足以调整原计划。

实测演示：2025-12-20 20:00截止，25号近10圈中位数58.623秒、22号58.338秒，25号慢0.285秒/圈；180秒假定损失约3.070个25号正常圈。三个车样本不能证明全场干净窗口。

如果尚不能确定最优窗口，也要先给已经算出的配速/成本/可执行备选，再指出使选择进一步明确的最少缺项。避免每轮重复“缺逐圈、燃油、驾驶时长、排班”；先补查询接口。没有变化则一句话保留上次建议，不为了显得有内容反复刷新空洞倒计时。
